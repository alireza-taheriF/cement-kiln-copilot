## 1. خلاصهٔ اجرایی

**Cement Kiln Copilot** یک سامانهٔ **پشتیبان تصمیم** برای بهینه‌سازی کوره و آسیاب سیمان است. سیستم، سری‌های زمانی فرآیند و (در طراحی) دادهٔ آزمایشگاه را می‌گیرد، مدلی برای پیش‌بینی یک KPI کلیدی آموزش می‌دهد، و به اپراتور **پیشنهادهای رتبه‌بندی‌شده برای تغییر ست‌پوینت** می‌دهد.

حلقهٔ اصلی از ابتدا تا انتها پیاده شده است:

ورود داده → ذخیره در دیتابیس → مهندسی ویژگی → آموزش مدل → API پیش‌بینی و توصیه → داشبورد Streamlit دو زبانه (فارسی / انگلیسی)

وضعیت محصول امروز: **MVP دمو‌پذیر و مشاوره‌ای (open-loop)**. برای دمو روی دادهٔ مصنوعی bundled کار می‌کند. هنوز کنترلر حلقه‌بسته نیست، به DCS وصل نمی‌شود، و روی دادهٔ واقعی کارخانه اعتبارسنجی نشده است.

جایگاه درست در بازار ایران: نه رقیب ABB Expert Optimizer یا APC کامل، بلکه **نظر دوم رتبه‌بندی‌شده برای اپراتور کوره**؛ کم‌ریسک از نظر OT، قابل استقرار در کارخانه، و نقطهٔ ورود به قرارداد پایلوت ۴ تا ۸ هفته.

## 2. مسئله‌ای که محصول حل می‌کند

پخت کلینکر (pyroprocessing) و آسیاب، فرآیندهایی انرژی‌بر، غیرخطی و حساس به تغییرات کوچک کنترل هستند. اپراتور شیفت باید هم‌زمان این‌ها را متعادل کند:

| محور | مثال‌ها | پیامد اگر بد تنظیم شود |
| ---- | ------- | ---------------------- |
| کیفیت کلینکر | آهک آزاد، C3S، نرمی Blaine | برگشت محصول، نارضایتی مشتری |
| انرژی | مصرف حرارتی ویژه، kWh/t | فشار روی حاشیه سود |
| ظرفیت و پایداری | upset کوره، تشکیل رینگ | توقف خط و افت در دسترس بودن |
| آلایندگی | NOx، CO | جریمه، محدودیت ظرفیت |

داده‌ها معمولاً در historian کارخانه موجود است. کمبود اصلی **راهنمای پیش‌رو** است: اپراتور نمی‌بیند یک تغییر ۵ درصدی در دبی سوخت، ده تا بیست دقیقه بعد با دمای زون پخت یا انرژی ویژه چه می‌کند.

سیستم‌های APC کلاسیک گران، طولانی‌مدت و از نظر امنیتی/بیمه‌ای سنگین‌اند. Copilot این شکاف را با یک ابزار **مشاوره‌ای** پر می‌کند: پیش‌بینی KPI، سپس رتبه‌بندی کاندیداهای ست‌پوینت، بدون نوشتن روی DCS.

## 3. محصول چیست و چه نیست

### چیست

- سامانهٔ **مشاورهٔ بازحلقه** (operator-in-the-loop)
- پیش‌بینی کوتاه‌مدت یک KPI از روی پنجرهٔ اخیر سیگنال‌ها
- تولید و امتیازدهی کاندیداهای ست‌پوینت با **همان مدل آموزش‌دیده** (نه قاعدهٔ سرانگشتی جدا)
- API نسخهٔ `v1` برای اتصال به UI یا سیستم‌های دیگر
- داشبورد اپراتور با RTL فارسی
- کیت فروش کارخانه (وان‌پیجر، ایمیل، اسکریپت جلسه، چک‌لیست کشف، پیش‌نویس PoC)

### چه نیست

- کنترلر حلقه‌بسته یا APC
- سامانهٔ ایمنی (SIS)
- جایگزین اینترلاک، PLC یا SCADA
- محصول تضمین‌کنندهٔ درصد صرفه‌جویی انرژی
- موتور بهینه‌سازی مقید صنعتی (فعلاً جستجوی شبکه‌ای محدود است)
- کانکتور آماده به PI / OPC-UA / Wonderware

جملهٔ کلیدی فروش و استقرار:

> سامانه ست‌پوینت **پیشنهاد** می‌دهد؛ اپراتور تصمیم می‌گیرد؛ **هیچ فرمانی به تجهیزات ارسال نمی‌شود.**

این محدودیت، نقطهٔ ضعف محصول نهایی نیست؛ **شرط فروش اول** در کارخانه‌های ایرانی است.

## 4. ارزش پیشنهادی

برای مدیر تولید / مهندس فرآیند:

1. دید ۱۰ تا ۳۰ دقیقه‌ای به مسیر KPI انتخاب‌شده
2. مقایسهٔ چند گزینهٔ ست‌پوینت به‌جای آزمون‌وخطای شیفت
3. یکنواختی بیشتر بین شیفت‌ها (کمتر وابسته به تجربهٔ فرد)
4. استقرار کم‌ریسک کنار ابزارهای موجود، بدون پروژهٔ چندساله اتوماسیون

برای IT/OT:

- داده فقط خواندنی است
- استقرار روی VM داخلی یا DMZ ممکن است
- احراز هویت سازمانی و نوشتن روی کنترل در فاز پایلوت لازم نیست

برای هلدینگ سیمان:

- نقطهٔ شروع دیجیتال‌سازی انرژی بدون تعهد APC
- قابلیت تکرار روی خطوط دیگر بعد از یک پایلوت موفق

## 5. معماری سیستم

معماری **ماژولار و لایه‌ای** است؛ هر لایه جدا قابل تست و تعویض است.

```
منابع داده
  DCS / historian (سری زمانی)  +  آزمایشگاه QC
                 │
                 ▼
        data_ingest
   اسکیما → لودر → پاک‌سازی
                 │
                 ▼
             db (SQLAlchemy)
        Tag / Signal / LabResult
                 │
                 ▼
               ml
  ویژگی → آموزش → ارزیابی → توصیه
                 │
        ┌────────┴────────┐
        ▼                 ▼
      api              dashboard
   FastAPI v1         Streamlit
 سلامت / پیش‌بینی / توصیه
```

| لایه | بسته | مسئولیت |
| ---- | ---- | -------- |
| ورود داده | `src/data_ingest` | اعتبارسنجی CSV، پاک‌سازی، تراز با آزمایشگاه، درج در DB |
| ماندگاری | `src/db` | مدل‌های ORM و نشست SQLAlchemy |
| یادگیری ماشین | `src/ml` | ویژگی، مدل، آموزش، ارزیابی، توصیه |
| سرویس | `src/api` | FastAPI نسخهٔ `v1` |
| رابط اپراتور | `src/dashboard` | داشبورد Streamlit |

جریان زمان اجرا در دمو:

1. `scripts/train_demo_model.sh` فایل `data/demo_signals.csv` را در SQLite می‌کارد و مدل را آموزش می‌دهد.
2. آرتیفکت `artifacts/models/kiln_zone1_temp_model.joblib` ذخیره می‌شود.
3. API با `MODEL_PATH` همان فایل را لود و در حافظه کش می‌کند.
4. داشبورد با HTTP به API وصل می‌شود؛ مدل را خودش لود نمی‌کند.

## 7. لایهٔ ورود داده

مرز قرارداد داده با دنیای بیرون اینجاست. پایین‌دست فرض می‌کند ورودی تمیز و تایپ‌شده است.

### ۷.۱ قرارداد CSV سیگنال (فرمت long / tidy)

ستون‌های اجباری:

| ستون | معنی |
| ---- | ---- |
| `timestamp` | زمان نمونه |
| `tag_name` | شناسهٔ تگ |
| `value` | مقدار عددی |

هر ردیف با `SignalCSVRow` (Pydantic) اعتبارسنجی می‌شود: تگ غیرخالی، مقدار عددی، زمان قابل پارس.

همین فرمت، فرمت دمو (`data/demo_signals.csv`) و فرمت مورد انتظار آموزش است.

### ۷.۲ قرارداد CSV آزمایشگاه

ستون‌های اجباری لودر تولید: `timestamp`, `parameter`, `value`, `sample_id`.

> توجه: فایل `data/sample_lab.csv` فعلاً **wide** است (`free_lime_pct`, `c3s_pct`, …) و با لودر تولید هم‌خوان نیست. برای پایلوت واقعی باید به فرمت long تبدیل شود یا لودر wide اضافه شود.

### ۷.۳ پاک‌سازی (`clean_signals`)

به‌صورت محافظه‌کارانه، per-tag:

1. مرتب‌سازی زمانی
2. حذف تکراری `(timestamp, tag)` با نگه‌داشتن آخرین مقدار
3. برش پرتی با z-score پیش‌فرض ۴ (winsorize، نه حذف ردیف)
4. درون‌یابی خطی شکاف‌های کوتاه (`limit=3`)

### ۷.۴ تراز سیگنال و آزمایشگاه

`align_signals_with_lab` با `merge_asof` نزدیک‌ترین نمونهٔ آزمایشگاه را در بازهٔ پیش‌فرض ±۳۰ دقیقه به سیگنال می‌چسباند. این تابع وجود دارد اما **در مسیر آموزش فعلی صدا زده نمی‌شود**.

### ۷.۵ ذخیره در دیتابیس

- تگ دیده‌نشده به‌صورت خودکار با `type="process"` ساخته می‌شود
- سیگنال‌ها bulk-insert می‌شوند
- نتایج آزمایشگاه جداگانه در `lab_results` می‌روند

اسکریپت دمو قبل از کاشت، جداول را drop و دوباره می‌سازد تا اجرا تکرارپذیر باشد.

## 8. پایگاه داده

طراحی **تگ‌محور و نرمال** است.

### جدول `tags`

فرادادهٔ هر سیگنال: نام یکتا، واحد، شرح، نوع (`process | setpoint | control | derived`)، پرچم `is_target`.

### جدول `signals`

جدول واقعیت سری زمانی. کلید مرکب `(ts, tag_id)` یعنی حداکثر یک مقدار در هر زمان برای هر تگ. ایندکس ثانویه `(tag_id, ts)` برای کشیدن تاریخچهٔ یک تگ.

### جدول `lab_results`

نمونه‌های نامنظم آزمایشگاه: `parameter`, `value`, `sample_id`, `notes`.

اتصال از `DATABASE_URL` خوانده می‌شود؛ اگر نباشد، پیش‌فرض توسعه `sqlite:///./cement_copilot_dev.db` است. برای تولید، PostgreSQL با `psycopg2` در نظر گرفته شده.

`config/db_config.yaml` پیش‌فرض‌های ساختاری را نگه می‌دارد؛ **رمز عبور نباید در YAML باشد** (از `.env` بیاید).

## 9. لایهٔ یادگیری ماشین

هدف آموزش: پیش‌بینی مقدار آیندهٔ یک تگ هدف از روی تگ‌های ورودی.

پیکربندی دمو در `config/model_config.yaml`:

| کلید | مقدار دمو | معنی |
| ---- | --------- | ---- |
| `target_tag` | `KILN_ZONE1_TEMP` | KPI پیش‌بینی‌شونده |
| `input_tags` | دمای زون ۱ و ۲ + دبی سوخت | ویژگی‌ها؛ تگ هدف می‌تواند برای ویژگی خودهمبسته تکرار شود |
| `lags` | `[1, 3, 6]` | تأخیر بر حسب ردیف (نه دقیقهٔ تقویمی) |
| `rolling_windows` | `[3, 6]` | پنجرهٔ میانگین/انحراف/کمینه/بیشینه |
| `horizon` | `3` | `y[t] = target[t+3]` |
| `model_output_path` | `artifacts/models/kiln_zone1_temp_model.joblib` | خروجی |

فرض مهم: داده روی **شبکهٔ زمانی منظم** resample شده است. در دمو فاصلهٔ نمونه‌ها ۱ دقیقه است؛ پس افق ۳ یعنی حدود ۳ دقیقه. در کارخانه اگر داده ۵ دقیقه‌ای باشد، افق ۳ یعنی ۱۵ دقیقه. این باید در onboarding صریحاً تنظیم شود.

### ۹.۱ مهندسی ویژگی (`src/ml/features.py`)

1. Pivot از long به wide با ایندکس زمان
2. ویژگی تأخیر: `{tag}_lag_{n}`
3. ویژگی غلتان: `{tag}_roll_{mean|std|min|max}_{window}` با `min_periods = window` (بدون نشت از آینده)
4. هدف آینده‌نگر: `{tag}_h{horizon}`
5. حذف ردیف‌هایی که به‌خاطر تأخیر ابتدایی یا افق انتهایی NaN دارند

ترتیب ستون‌ها قطعی است تا آموزش و استنتاج یکی باشند.

### ۹.۲ مدل (`EnergyKPIModel`)

پوشهٔ خودتوصیف دور یک رگرسور:

- پیش‌فرض: LightGBM (`n_estimators=300`, `learning_rate=0.05`, `num_leaves=31`, `random_state=42`)
- اگر LightGBM نصب نباشد: RandomForest اسکیت‌لرن
- ترتیب ویژگی هنگام `predict` اجبار می‌شود
- متادیتا: زمان آموزش UTC، تعداد نمونه/ویژگی، نام بک‌اند
- ذخیره و بازیابی کل wrapper با joblib
- `get_feature_importance` برای توضیح‌پذیری اولیه (در UI فعلاً نمایش داده نمی‌شود)

### ۹.۳ آموزش (`src/ml/train.py`)

```bash
python -m src.ml.train --config config/model_config.yaml
```

مراحل: خواندن سیگنال از DB → ساخت `(X, y)` → تقسیم زمانی ۸۰/۲۰ بدون shuffle → برازش → RMSE/MAE/MAPE روی train و valid → ذخیرهٔ آرتیفکت → چاپ خلاصهٔ JSON.

تقسیم زمانی برای جلوگیری از نشت آینده به آموزش ضروری است.

### ۹.۴ ارزیابی

`rmse`, `mae`, `mape` (درصد؛ روی اهداف صفر محاسبه نمی‌شود). برای گیت CI و گزارش پایلوت قابل استفاده است.

## 10. موتور توصیهٔ ست‌پوینت

این بخش تمایز محصول است. هر کاندیدا با **مدل واقعی** امتیاز می‌گیرد، نه با قاعدهٔ اگر-آنگاه.

الگوریتم:

1. تگ‌های قابل تنظیم را حول ست‌پوینت فعلی با `step_fractions` Perturb می‌کند  
   مقدار جدید = `فعلی × (1 + f)` مثلاً `f = ±0.05` یعنی ±۵٪
2. در صورت وجود، با `absolute_bounds` کلیپ می‌کند
3. ضرب دکارتی ترکیب تگ‌ها را می‌سازد (سقف ۲۰۰ کاندیدا؛ خط پایه همیشه اول است)
4. مقدار هر تگ کاندیدا را در کل پنجرهٔ سیگنال long جایگزین می‌کند
5. همان ماتریس ویژگی پیش‌بینی را می‌سازد و مدل را اجرا می‌کند
6. امتیاز = میانگین قدرمطلق فاصلهٔ پیش‌بینی‌ها تا `desired_target` (**کمتر بهتر است**)
7. `top_k` بهترین را برمی‌گرداند

خروجی هر کاندیدا: ست‌پوینت‌ها، میانگین/کمینه/بیشینهٔ پیش‌بینی، امتیاز.

محدودیت مدل‌سازی توصیه (برای صداقت فنی در فروش مهم است):

- جستجو گسسته و شبکه‌ای است، نه بهینه‌ساز مقید (SLSQP، MPC، Bayesian)
- جایگزینی مقدار روی **کل پنجره** یعنی فرض «اگر این ست‌پوینت در کل این بازه حاکم بود»؛ شبیه‌سازی دینامیک فرآیند نیست
- قیود فرآیندی مثل حداقل O₂ یا حداکثر CO در امتیازدهی وارد نمی‌شوند مگر به‌صورت کران روی خود تگ قابل تنظیم
- تگ غیرقابل تنظیم در سیگنال ثابت می‌ماند؛ اثر متقابل واقعی کوره ساده‌سازی شده است

برای پایلوت اول همین کافی است، به شرطی که به مشتری به‌عنوان **what-if امتیازدهی‌شده** فروخته شود نه به‌عنوان شبیه‌ساز فیزیک کوره.

| `GET /health` | زنده بودن |
| `GET /ready` | آمادگی (فعلاً واقعی نیست؛ اتصال DB و مدل را چک نمی‌کند) |

| `POST /v1/recommend/setpoints` | توصیهٔ ست‌پوینت |

خطاهای قراردادی:

| کد | معنی |
| -- | ---- |
| `400` | ساخت ویژگی شکست خورد (تگ کم، پنجره کوتاه، …) |
| `422` | بدنهٔ نامعتبر Pydantic |
| `500` | `MODEL_PATH` خالی یا فایل مدل موجود نیست |

### ۱۱.۱ پیش‌بینی

درخواست حداقل ۲ timestamp و دیکشنری `signals` با آرایه‌هایی هم‌طول timestamps می‌خواهد.

پاسخ: `predictions[]`, `target_name`, `model_backend`, `model_version`, `n_rows`.

ویژگی‌های استنتاج از روی **نام ستون‌های ذخیره‌شده در مدل** بازسازی می‌شوند (`{tag}_lag_n` و `{tag}_roll_*_n`). بنابراین مدل آموزش‌دیده منبع حقیقت است، نه YAML در زمان سرو.

### ۱۱.۲ توصیه

علاوه بر سیگنال‌ها:

- `current_setpoints`
- `desired_target`
- `adjustable_tags` (هرکدام باید در current_setpoints باشد)
- `step_fractions` پیش‌فرض `[-0.10, -0.05, 0.0, 0.05, 0.10]`
- `top_k` پیش‌فرض ۳
- `absolute_bounds` اختیاری

پاسخ شامل میانگین پیش‌بینی خط پایه، تعداد کاندیداهای ارزیابی‌شده، و لیست رتبه‌بندی‌شده است.

نمونهٔ بدنه در [پیوست ب](#پیوست-ب-نمونه-درخواست-api).

## 17. چه کارهایی ارزش فروش را چند برابر می‌کند

ترتیب زیر بر اساس اثر روی قیمت قابل دفاع است، نه زیبایی مهندسی. اگر فقط سه کار بکنید، همان سه مورد اول را بکنید.

### سطح ۱ — ارزش را ۲ تا ۴ برابر می‌کند (الزامی قبل از فروش جدی)

**۱) یک پایلوت واقعی با عدد، حتی کوچک**

یک خط کوره، ۴ تا ۱۲ هفته خروجی historian، یک KPI مورد اعتماد کارخانه (دمای زون پخت یا پروکسی مصرف حرارتی). گزارش نهایی باید داشته باشد:

- خطای پیش‌بینی روی hold-out
- چند جلسهٔ توصیه در برابر نظر مهندس فرآیند («قابل اقدام» یا نه)
- در صورت امکان، مقایسهٔ قبل/بعد مصرف سوخت در بازهٔ محدود — بدون ادعای علیت اغراق‌شده

یک صفحهٔ «در کارخانهٔ X، روی خط Y» قیمت را از فروش سورس به فروش راه‌حل صنعتی عوض می‌کند.

**۲) کانکتور دادهٔ کارخانه**

حداقل یکی از این‌ها: خروجی استاندارد CSV از PI/Wonderware با مپر تگ، یا OPC-UA فقط‌خواندنی، یا کپی دوره‌ای از historian به Postgres. بدون این، هر دمو «نرم‌افزار آزمایشگاهی» دیده می‌شود.

**۳) بسته‌بندی استقرار داخل کارخانه**

`docker compose` با API + داشبورد + Postgres، فایل systemd، راهنمای OT یک‌صفحه‌ای (پورت‌ها، اینکه DCS نوشته نمی‌شود، محل لاگ). کارخانه برای نرم‌افزار بدون نصب مشخص پول جدی نمی‌دهد.

**۴) ایمنی توصیه‌ها به‌زبان فرآیند**

کران مطلق اجباری روی هر تگ قابل تنظیم، لیست تگ ممنوع، نمایش «این توصیه از کران مهندسی خارج است»، ثبت اینکه چه کسی توصیه را دیده. این‌ها فروش را از استارتاپ به ابزار شیفت نزدیک می‌کند.

### سطح ۲ — ارزش را ۴ تا ۸ برابر می‌کند (لایسنس سالانه)

**۵) KPIهای پولی، نه فقط دما**

مصرف حرارتی ویژه (kcal/kg کلینکر)، kWh فن/آسیاب، آهک آزاد، انحراف از باند کیفیت. مدیرعامل روی دمای زون پول نمی‌دهد؛ روی انرژی و کیفیت می‌دهد. دما می‌تواند متغیر میانی مدل بماند.

**۶) توضیح‌پذیری داخل داشبورد**

اهمیت ویژگی + دو جملهٔ فارسی: «کاهش سوخت پیشنهاد شده چون در ۲۰ دقیقهٔ اخیر دمای زون ۱ بالاتر از باند بوده و CO پایین مانده.» اپراتور بدون توضیح، توصیه را نادیده می‌گیرد و محصول می‌میرد.

**۷) حسابرسی و چندکاربره**

ورود ساده (حتی HTTP basic یا LDAP کارخانه)، نقش اپراتور / مهندس فرآیند / ناظر، ذخیرهٔ هر توصیه با payload و مدل‌ورژن. برای کمیتهٔ امنیت و برای ادعای «اثر پایلوت» حیاتی است.

**۸) بهینه‌سازی مقید به‌جای شبکهٔ ۵ نقطه‌ای**

حداقل: قیود O₂/CO/دمای حداکثری در امتیاز، جریمهٔ تغییرات بزرگ ست‌پوینت، و جستجوی هوشمندتر. داستان فروش از «what-if» به «بهینه‌سازی تحت قیود ایمنی» ارتقا می‌یابد — هنوز بدون حلقه‌بسته.

### سطح ۳ — ارزش را ۸ تا ۱۵ برابر می‌کند (قرارداد هلدینگ)

**۹) ماژول آسیاب و کولر**

کوره نقطهٔ ورود است؛ آسیاب برق می‌خورد و در ایران داستان انرژی الکتریکی قوی‌تری دارد. یک Copilot آسیاب جدا، upsell طبیعی خط دوم است.

**۱۰) سوخت جایگزین و خوراک متغیر**

کارخانه‌هایی که RDF یا سوخت جایگزین می‌سوزانند بیشترین درد فرآیند را دارند. اگر مدل رژیم خوراک/سوخت را ببیند، رقیب داخلی تقریباً ندارید.

**۱۱) گزارش شیفت و ROI عملیاتی**

خروجی PDF/Excel: توصیه‌های روز، چند بار اعمال شد، انحراف KPI، برآورد سوخت. این گزارش را مدیر انرژی به هیئت‌مدیره می‌برد؛ نرم‌افزار بدون این گزارش در حد دمو می‌ماند.

**۱۲) گواهی و شراکت، نه فقط کد**

همکاری با یک شرکت اتوماسیون معتبر ایرانی، استقرار در پارک فناوری، و مسیر ارزیابی امنیت OT. در مناقصهٔ هلدینگ غدیر یا سیمان تأمین، برند شریک بیشتر از مدل LightGBM قیمت را بالا می‌برد.

### کارهایی که ارزش را کم می‌کند (نکنید)

- ادعای «کوره را خودکار کنترل می‌کنیم» در جلسهٔ اول
- قول درصد ثابت صرفه‌جویی قبل از دیدن داده
- فروش سورس خام به کارخانه به‌جای خدمت + لایسنس
- رفتن به حلقه‌بسته قبل از اعتماد شیفت
- پنهان کردن مصنوعی بودن دادهٔ دمو

### اولویت ۹۰ روزه اگر هدف فروش است

| هفته | خروجی قابل فروش |
| ---- | --------------- |
| ۱–۲ | Docker Compose + راهنمای استقرار فارسی + مپر تگ CSV کارخانه |
| ۳–۶ | پایلوت آفلاین روی دادهٔ واقعی یک کارخانه یا دادهٔ نزدیک‌به‌واقعی با NDA |
| ۷–۸ | داشبورد: کران ایمنی، اهمیت ویژگی، ذخیرهٔ جلسهٔ توصیه |
| ۹–۱۰ | گزارش پایلوت یک‌صفحه‌ای با متریک و نقل‌قول مهندس فرآیند |
| ۱۱–۱۲ | بستهٔ تجاری: PoC قیمت‌دار، لایسنس سالانه، قرارداد پشتیبانی |

با همین مسیر، محصول از «ریپوی خوب» به «راه‌حل قابل فاکتور» تبدیل می‌شود. پرش مستقیم به APC یا پلتفرم چندکارخانه، فروش را عقب می‌اندازد.

## 18. قیمت‌گذاری در ایران

اعداد زیر **برآورد بازار ۱۴۰۴–۱۴۰۵** برای نرم‌افزار صنعتی B2B است، نه پیشنهاد مالی قطعی. تورم و نرخ ارز را در لحظهٔ قرارداد به‌روز کنید. واحد: **میلیون تومان**.

مرجع ذهنی بازار:

- سیستم APC/بهینه‌ساز کورهٔ خارجی در شرایط عادی بین‌المللی معادل صدها هزار دلار است و در ایران به‌خاطر تحریم و ارز practically نایاب است.
- کارخانهٔ سیمان هزینهٔ انرژی و توقف خط را خوب می‌فهمد؛ برای نرم‌افزار «بدون عدد» سخت پول می‌دهد.
- خریدار واقعی معمولاً مدیر کارخانه + مهندسی فرآیند است؛ IT فقط وتوی امنیت دارد.
- سقف پرداخت پایلوت بدون مصوبهٔ هلدینگ معمولاً پایین‌تر از لایسنس سالانه است.

### ۱۸.۱ ارزش محصول در وضعیت فعلی (MVP دمو)

| شیوهٔ فروش | بازهٔ معقول | توضیح |
| ---------- | ----------- | ----- |
| فروش سورس / واگذاری کد به شرکت اتوماسیون | ۸۰ تا ۲۵۰ | یک‌بار؛ بدون برند و بدون دادهٔ کارخانه |
| دمو + مشاورهٔ یک‌روزه در سایت | ۱۵ تا ۴۰ | برای باز کردن در، نه درآمد اصلی |
| پایلوت ۴–۸ هفته روی CSV (بدون تعهد صرفه‌جویی) | ۱۵۰ تا ۴۰۰ | بهترین قیمت امروز اگر یک کارخانه حاضر به داده باشد |
| اشتراک ماهانهٔ ابری | مناسب نیست | کارخانهٔ سیمان داده را از OT بیرون نمی‌دهد |

اگر کسی بالای ۵۰۰ میلیون برای **همین ریپو بدون دادهٔ واقعی** بدهد، یا ارزش را اشتباه فهمیده یا در حال خرید تیم/ایده است نه نرم‌افزار آماده.

### ۱۸.۲ بعد از سطح ۱ (پایلوت واقعی + استقرار داخل کارخانه)

| آیتم | بازه | مدل پیشنهادی |
| ---- | ---- | ------------ |
| PoC اندازه‌گیری‌شده ۶–۸ هفته، یک خط | ۳۰۰ تا ۷۰۰ | ثابت؛ ۲۰–۳۰٪ پیش‌پرداخت |
| لایسنس سال اول یک خط (نرم‌افزار + استقرار + آموزش) | ۸۰۰ تا ۲۰۰۰ | جدا از PoC یا با کسر بخشی از هزینهٔ PoC |
| پشتیبانی و به‌روزرسانی سال بعد | ۲۰–۳۰٪ لایسنس | حداقل یک بازدید فصلی + ریموت |
| خط / کارخانهٔ اضافه | ۵۰–۷۰٪ خط اول | چون مدل از نو آموزش می‌بیند ولی پلتفرم تکرار می‌شود |

### ۱۸.۳ بعد از سطح ۲ و ۳ (KPI پولی + چند ماژول + هلدینگ)

| آیتم | بازه |
| ---- | ---- |
| لایسنس سالانهٔ یک خط کامل (کوره + گزارش انرژی) | ۱٫۵ تا ۴ میلیارد تومان |
| قرارداد چارچوب هلدینگ ۳ تا ۸ خط، سه ساله | ۵ تا ۱۵ میلیارد (کل دوره)، با فازبندی |
| ماژول آسیاب یا سوخت جایگزین | ۳۰–۵۰٪ اضافه‌بها روی خط |
| سهم از صرفه‌جویی (اختیاری، بعد از baseline) | ۱۰–۲۰٪ صرفه‌جویی اثبات‌شده سال اول، با سقف و کف |

مدل سهم از صرفه‌جویی را **قبل از داشتن اندازه‌گیری مشترک سوخت** پیشنهاد نکنید؛ در ایران روی تعریف baseline دعوا می‌شود.

### ۱۸.۴ لنگر ارزش برای مذاکره

یک کارخانهٔ متوسط را فرض کنید. حتی با سوخت یارانه‌ای، ۱ درصد بهبود مصرف حرارتی یا کاهش توقف‌های کوچک، در مقیاس سال معمولاً از هزینهٔ لایسنس بالاتر است. در جلسه این را به‌صورت **سقف ارزش** بگویید، نه تعهد شما:

> «اگر فقط بخشی از ناپایداری شیفت یا over-fueling کم شود، پایلوت خودش را برمی‌گرداند. عدد دقیق را بعد از داده می‌سنجیم؛ الان درصد تضمین نمی‌کنیم.»

این جمله هم قیمت را بالا نگه می‌دارد هم از شکایت بعدی جلوگیری می‌کند.

### ۱۸.۵ قیمت‌گذاری پیشنهادی شما در ۱۲ ماه آینده

فرض: هنوز case study عمومی ندارید.

1. **الان تا پایلوت اول:** PoC را ۱۵۰–۳۰۰ میلیون بفروشید حتی اگر کم‌سود باشد. هدف دارایی است نه حاشیه: داده، نقل‌قول، اسکرین‌شات واقعی.
2. **بعد از پایلوت موفق:** قیمت PoC بعدی را به ۴۰۰–۶۰۰ میلیون برسانید و لایسنس سالانه را جدا فاکتور کنید (از حدود ۱ میلیارد).
3. **تخفیف ندهید روی «مشاوره‌ای بودن».** مشاوره‌ای بودن هزینه را کم نمی‌کند؛ ریسک حقوقی کارخانه را کم می‌کند و باید گران‌تر از یک اسکریپت باشد.
4. **سورس را نفروشید** مگر به integrator با قرارداد لایسنس محدود و حق استقرار در N سایت. فروش سورس یک‌باره، سقف ارزش را می‌کشد.

### ۱۸.۶ هزینهٔ تمام‌شدهٔ تحویل که باید در قیمت بیاید

در قیمت پایلوت این‌ها را حساب کنید و گرنه ضرر می‌کنید:

- رفت‌وآمد و اقامت سایت
- وقت مهندس فرآیند کارخانه (باید در فرضیات قرارداد باشد)
- پاک‌سازی دادهٔ کثیف historian (معمولاً بیش از آموزش مدل طول می‌کشد)
- جلسات امنیت OT و NDA
- یک نفر پشتیبانی شیفت در دو هفتهٔ پایانی پایلوت

قانون سرانگشتی: قیمت فروش ≥ ۳ برابر هزینهٔ مستقیم همان تحویل، وگرنه محصول را ارزان قفل کرده‌اید.

## 19. نحوهٔ فروش

### ۱۹.۱ چه چیزی می‌فروشید (بسته، نه ریپو)

بستهٔ قابل فاکتور:

1. نرم‌افزار مشاوره‌ای نصب‌شده روی VM کارخانه
2. مدل آموزش‌دیده روی تگ‌های همان خط
3. آموزش ۲ ساعته به اپراتور و مهندس فرآیند
4. گزارش هفتگی پایلوت
5. پشتیبانی در ساعت اداری

کد گیت‌هاب پیش‌نمایش اعتماد است؛ قلم فاکتور نیست.

### ۱۹.۲ خریدار و مسیر تصمیم

| نقش | چه می‌خواهد | خطر وتو |
| --- | ----------- | ------- |
| مدیر تولید / رئیس کوره | پایداری شیفت، کمتر بودن upset | کم؛ حامی عملیاتی |
| مهندس فرآیند | مدل معقول، کران ایمنی، نه جعبه سیاه | اگر «غیر فیزیکی» ببیند می‌کشد |
| مدیر انرژی / محیط زیست | عدد سوخت و انتشار | حامی بودجه اگر KPI پولی باشد |
| IT/OT | هیچ نوشتنی روی DCS، داده داخل سایت | بزرگ‌ترین ترمز |
| بازرگانی / تدارکات | استعلام، کد تأمین‌کننده | بعد از PoC |
| هلدینگ | تکرارپذیری روی چند کارخانه | برای قرارداد بزرگ |

هدف جلسهٔ اول: مهندس فرآیند + مدیر تولید. IT را برای جلسهٔ دوم بیاورید با پیام «فقط خواندنی».

### ۱۹.۳ قیف فروش پیشنهادی

```
لیست ۳۰ کارخانه / هلدینگ
        → ایمیل سرد یا معرفی شتاب‌دهنده / شریک اتوماسیون
        → تماس ۲۰ دقیقه‌ای
        → دمو ۱۰ دقیقه‌ای زنده (اسکریپت موجود)
        → جلسهٔ کشف ۴۵ دقیقه‌ای (چک‌لیست موجود)
        → NDA + نمونهٔ historian ناشناس
        → پیش‌نویس PoC
        → پایلوت ۴–۸ هفته
        → گزارش go/no-go
        → لایسنس سالانه + خط دوم
```

از دمو مستقیم به «قرارداد سه میلیاردی» نپرید. در صنعت سیمان ایران، بدون پایلوت داخل سایت practically فروشی در آن سطح نیست.

### ۱۹.۴ کانال‌ها

**کانال مستقیم**

کارخانه‌های دارای کورهٔ خشک و درد انرژی/کیفیت: مجموعه‌های بزرگ‌تر (هلدینگ‌های سیمان)، کارخانه‌های با سوخت جایگزین، خطوطی که اخیراً APC خارجی‌شان از سرویس افتاده.

پیام موضوع ایمیل (از کیت موجود): تصمیم‌یار ست‌پوینت کوره — فقط مشاوره‌ای، بدون نوشتن روی DCS.

**کانال شریک**

شرکت‌های اتوماسیون، integratorهای PCS7/ABB/Schneider داخل ایران، مشاوران انرژی صنایع کانی. شما مدل و UI را می‌دهید؛ آن‌ها رابطه و دسترسی OT را. سهم: معمولاً ۱۵–۳۰٪ قرارداد برای شریک معرفی‌کننده، یا قرارداد سفید با برند مشترک.

**کانال نهادی**

برنامه‌های بهینه‌سازی انرژی وزارت صمت، ایمیدرو، شهرک‌های علمی‌تحقیقاتی، صندوق نوآوری. این کانال کند است اما برای اعتبار و هزینهٔ پایلوت اول مفید است. اینجا محصول را «ابزار کاهش شدت انرژی صنایع انرژی‌بر» بسته کنید.

**کانالی که اولویت ندارد**

فروش به استارتاپ‌های عمومی AI، مارکت‌پلیس افزونه، یا کارخانهٔ سیمان سفید خیلی کوچک بدون historian. چرخهٔ فروش می‌سوزد.

### ۱۹.۵ روایت جلسه (یک دقیقه)

> کوره غیرخطی است و اپراتور بدون دید جلو سوخت و کیفیت را سبک‌سنگین می‌کند. ما روی دادهٔ خودتان مدل می‌زنیم، ده دقیقه بعد KPI را پیش‌بینی می‌کنیم، و چند ست‌پوینت را رتبه می‌دهیم. شما تصمیم می‌گیرید. به PLC وصل نمی‌شویم. در هشت هفته روی یک خط معلوم می‌شود به درد شیفت می‌خورد یا نه. درصد انرژی قول نمی‌دهیم؛ اندازه‌گیری می‌کنیم.

بعد دمو. بعد بپرسید KPI اول چیست، نه اینکه «چقدر بودجه دارید».

### ۱۹.۶ اعتراض‌های رایج و پاسخ

| اعتراض | پاسخ |
| ------ | ---- |
| APC داریم / داشتیم | ما جایگزین کنترلر نیستیم؛ نظر دوم روی همان دادهٔ historian هستیم. |
| داده محرمانه است | پایلوت داخل سایت، بدون ابر، NDA، در صورت نیاز ناشناس‌سازی تگ. |
| مدل غلط بدهد کوره آسیب می‌بیند | توصیه است؛ کران مهندسی شما اعمال می‌شود؛ بدون تأیید اپراتور هیچ تغییری نیست. |
| عدد صرفه‌جویی چقدر است؟ | نمی‌دانیم تا داده را ببینیم. پایلوت برای همین است. |
| Streamlit برای کارخانه ضعیف است | برای پایلوت عمداً سبک است؛ HMI اختصاصی فاز بعد از go است. |
| چرا این‌قدر؟ یک داشبورد پاوربی‌آی ارزان‌تر است | شما پیش‌بینی و what-if امتیازدهی‌شده می‌خرید، نه نمودار گذشته. |

### ۱۹.۷ قرارداد؛ بندهایی که باید باشد

- محدوده: یک خط، یک KPI، حداکثر N تگ قابل تنظیم
- صراحت open-loop و سلب مسئولیت ایمنی
- مالکیت داده با کارخانه؛ حق استفاده از مدل فقط برای همان سایت مگر خلافش نوشته شود
- تأخیر دسترسی داده، تقویم پایلوت را به‌اندازهٔ همان تأخیر جابه‌جا می‌کند
- معیار موفقیت از قبل: مثلاً «مهندس فرآیند حداقل M جلسه را قابل اقدام بداند» نه «۲٪ سوخت»
- ممنوعیت تبلیغ نام کارخانه بدون اجازه؛ با اجازه، case study قیمت بعدی شما را می‌سازد

### ۱۹.۸ آنچه باید در پیشنهاد قیمت ننویسید

- تضمین ROI
- اتصال حلقه‌بسته
- پشتیبانی ۲۴×۷ مگر جدا فاکتور شود
- آموزش مدل برای کل هلدینگ با قیمت یک خط

### ۱۹.۹ شاخص سلامت فروش (برای خودتان)

اگر در ۹۰ روز هیچ‌کدام از این‌ها نشد، کانال یا پیام غلط است نه «بازار سیمان پول ندارد»:

- حداقل ۵ جلسه با مهندس فرآیند
- حداقل یک NDA
- حداقل یک نمونهٔ historian (حتی دو هفته، حتی ناقص)

بازار داخلی سیمان برای ابزار انرژی خالی است؛ گلوگاه دسترسی OT و اعتماد است، نه نبود درد.

## 20. پیوست‌ها

### پیوست الف. تگ‌های دمو و معنی تقریبی

| تگ | نقش در دمو |
| -- | ---------- |
| `KILN_ZONE1_TEMP` | هدف پیش‌بینی (زون پخت ۱) |
| `KILN_ZONE2_TEMP` | ورودی کمکی |
| `KILN_FUEL_FLOW` | ورودی و تگ قابل تنظیم توصیه |

در کارخانه این نام‌ها به تگ‌های واقعی historian نگاشت می‌شوند (مثلاً دمای burning zone، دبی گاز/مازوت، سرعت فن ID، خوراک کوره، O₂ خروجی).

### پیوست ب. نمونه درخواست API

پیش‌بینی:

```json
{
  "timestamps": ["2026-01-01T00:00:00", "2026-01-01T00:01:00"],
  "signals": {
    "KILN_ZONE1_TEMP": [1380.4, 1382.2],
    "KILN_ZONE2_TEMP": [1322.9, 1324.0],
    "KILN_FUEL_FLOW": [42.3, 42.6]
  }
}
```

در عمل باید تعداد ردیف از بزرگ‌ترین lag/rolling بیشتر باشد (در دمو مثلاً حدود ۶۰ ردیف).

توصیه: همان سیگنال‌ها به‌اضافه:

```json
{
  "current_setpoints": { "KILN_FUEL_FLOW": 42.6 },
  "desired_target": 1380.0,
  "adjustable_tags": ["KILN_FUEL_FLOW"],
  "step_fractions": [-0.1, -0.05, 0.0, 0.05, 0.1],
  "top_k": 3,
  "absolute_bounds": { "KILN_FUEL_FLOW": [35.0, 50.0] }
}
```

### پیوست ج. اجرای تست و دمو برای ارائه به مشتری

قبل از هر جلسه:

```bash
pytest -q
./scripts/train_demo_model.sh
./scripts/run_demo.sh
```
